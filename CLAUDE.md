# Backrooms

## What is Backrooms?

Backrooms is a shared memory layer for AI coding agents. The name is inspired by the backrooms conspiracy theory — infinite corridors where you're always lost. That's exactly what AI agents are today: every tool is its own isolated corridor with no exits, no shared memory, no way to pass context between them.

Backrooms fixes this by introducing **rooms** — named, persistent shared spaces that any agent can join, push messages to, and pull context from, regardless of which tool they're in or which directory they're working in.

The mental model is git. Just like `.git` initializes a repository, `.backroom.json` initializes a room in a directory. Any agent that opens that directory can join the room and immediately access everything that's been discussed there — across Claude Code, Cursor, OpenCode, Codex, or any MCP-compatible tool.

---

## The Core Problem

AI agents are stateless across sessions and siloed across tools:

- Claude Code doesn't know what you discussed in Cursor yesterday
- Opening a new terminal loses all context from the previous session
- Switching from Claude Code to OpenCode means re-explaining everything from scratch
- Working across multiple repos in one project means fragmented context per directory

Backrooms solves all of these by maintaining a persistent, tool-agnostic message log per room.

---

## Architecture Overview

```
.backroom.json (local room anchor, like .git)
        ↓
MCP Server / plugin (FastMCP, Python)
        ↓
PostgreSQL (rooms, messages, summaries, members)
        ↑
Claude Code / Cursor / OpenCode / Codex
all connect via MCP tools
```

Browser sessions (Claude.ai) are handled via a Chrome extension that pushes sessions into rooms manually.

## Modules

### 1. Room Management (COMPLETE — spec locked)
Handles the full lifecycle of rooms: create, join, switch, exit.

Key tools:
- `init_room(name)` — creates room, writes `.backroom.json`
- `join_room()` — reads `.backroom.json`, registers agent as member, returns room summary
- `get_current_room()` — confirms active room and server connection
- `exit_room()` — deletes `.backroom.json`, deregisters from room
- `list_rooms()` — returns all rooms for this user

`.backroom.json` schema:
```json
{
  "id": "roomid", 
  "name": "room-name",
  "owner": "github-user-id",
  "created_at": "ISO timestamp"
}
```

### 2. Messaging (SPEC LOCKED — implementation next)
Handles pushing and pulling messages from a room.

Key tools:
- `push_message(user_content, assistant_content)` — pushes a user+assistant turn as two rows in one transaction
- `pull_messages(limit, offset, after_id)` — retrieves messages with pagination

Push behavior:
- Room resolved from `.backroom.json` automatically
- Two rows inserted per call (role: user, role: assistant) in a single transaction
- Token accumulation tracked on room record (estimated as len(content) / 4)
- Returns `{ status: "ok" }` normally
- Returns `{ status: "summary_needed", last_summarized_message_id, unsummarized_message_count }` when tokens since last summary exceed 8000

Pull behavior:
- Default: last 20 messages, chronological order
- Supports limit, offset for pagination
- Supports after_id for fetching unsummarized messages during summary generation

### 3. Summary (NOT YET SPECCED)
Maintains a derived summary layer per room. Summaries are generated by agents, not the server.

Planned tools:
- `submit_summary(content, from_message_id, to_message_id)` — stores agent-generated summary
- `summarize_room()` — manual trigger, agent reads messages and generates summary on demand

Summary is returned as part of `join_room` response so agents are oriented immediately on session start.

### 4. Visibility (NOT YET SPECCED)
Activity feed showing which agents used which tools and when. Surfaces in a dashboard so users can see Backrooms is actively working.

## Stack

- **Backend / MCP Server**: FastMCP 2.0 (Python)
- **Database**: PostgreSQL with pgvector (for future semantic search)
- **Auth**: GitHub OAuth (user_id derived from GitHub account)
- **Chrome Extension**: Vanilla JS (for browser session export)
- **Dashboard**: Next.js (visibility layer, not yet started)

## Agent Instructions

These rules apply to every session in any directory containing a `.backroom.json`:

**At session start:**
1. Call `get_current_room()` to check active room
2. If `.backroom.json` exists, call `join_room()` immediately
3. Call `pull_messages(limit=20)` to load recent context
4. Confirm which room you joined before doing anything else

**During session:**
5. After EVERY assistant response, call `push_message(user_content, assistant_content)`
6. If push_message returns `status: "summary_needed"`, call `pull_messages(after_id=last_summarized_message_id)` to get unsummarized messages, generate a summary, then call `submit_summary`

**Room management:**
7. If no `.backroom.json` exists, present options: init new room, join existing (linked), join existing (floating), or list rooms
8. Never switch rooms or exit without explicit user confirmation
9. Always confirm room changes in chat — never silent

**Never:**
- Push messages to a room without confirming it exists
- Call push_message with only one of user_content or assistant_content null unless explicitly told to
- Assume a room is active without reading `.backroom.json` first

## What Help is Needed from Claude

### During implementation sessions:

**Room Management (current focus):**
- Help implement `init_room`, `join_room`, `get_current_room`, `exit_room`, `list_rooms` in `tools/room_management.py`
- Help write PostgreSQL migrations for rooms and room_members tables
- Help debug FastMCP mount issues (we use `mcp.mount(router)` not `include_router`)
- Help test that DB context from lifespan state is accessible inside mounted routers

**Messaging (next):**
- Help implement `push_message` and `pull_messages` in `tools/messaging.py`
- Help write the token accumulation logic and summary_needed signal
- Help write PostgreSQL migrations for messages table and rooms table additions

**General:**
- Always read `.backroom.json` at session start and join the active room
- Push every turn to the room so context is shared
- When asked to implement something, check the PRD files in `prds/` first for spec details
- Prefer flat, simple implementations — no premature abstraction
- Use async/await throughout (FastMCP tools are async)
- Use the existing `config/db.py` connection pattern for all DB access

### Project conventions:
- Each tool module is a separate `FastMCP` instance mounted onto the parent in `server.py`
- DB connection accessed via `ctx.request_context.lifespan_state["db"]`
- All tool descriptions must start with ALWAYS or NEVER for strong agent signal
- `.backroom.json` is always read from the agent's current working directory
